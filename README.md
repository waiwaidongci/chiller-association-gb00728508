# 制冷机维保告警联查

澄港区域供冷运维中心 · 设备可靠性组。东站、西站两座机房各有 8 台冷水机组，为商务区和数据机房供冷。值班员从楼控导出运行分钟和班初告警快照，设备可靠性组补齐计划负荷档并联合核对提报，复核员把联查顺序交给夜班维保。

每台机组每天一条记录，观测窗口为当天有有效告警监测的运行时段。计划负荷用窗口开始前的机组排程负荷率分档，低于 75% 为低负荷，其余为高负荷。伴随告警取当天首次有效运行观测开始时的记录，目录为冷凝水流量低、压缩机电流偏高、冷冻水压差低，多项用竖线 | 分开，确认全无填“无”。三项均需有可靠记录，缺测的运行分钟与事件应先从统计范围扣除，无法确认班初快照的机组日不得入表。目标事件是观测开始后新发的蒸发器出水温度高，按机组和事件时间去重，同秒最多一条。 交付按告警分列的达标层粗率比、直接标准化率比与逐层事件及监测小时底账。设备复核员按支持度和关联方向排查机组运行资料，再将批准后的联查报告送交夜班维保。

- 班组按告警条数排序，12 小时开机和 6 小时开机的数据混在一起。
- 冷凝水流量低常出现在高负荷日，全站粗率差容易被当成同工况的差异。
- 手工透视表会把同一机组日的多项伴随告警拆成多行，事件和小时数随之重复累加。

## 六个业务模块

1. 供冷联查总览
2. 机组监测底账
3. 暴露率比计算
4. 分层对照明细
5. 维保联查复核
6. 联查报告分发

## 工作剧本

1. 08:10 值班员核对 2 座机房的 16 台机组，检查 10 月 12 日至 17 日的计划负荷与有效监测时段。
2. 08:35 分析员导入《澄港制冷_20261012-1017_监测底账.csv》的 96 条机组日记录，总有效监测 864 小时。
3. 09:00 提交分析，每层有无告警两组各至少 24 小时，两组合计至少 3 起目标新发事件。
4. 09:20 检查冷凝水流量低的 4 个达标层，查看粗率比和标准化率比的差别，再核对冷冻水压差低每层仅 14 小时的有告警底数。
5. 10:15 设备复核员从 2 项可报告的伴随告警中优先复核压缩机电流偏高，并调阅同负荷机组日志。
6. 11:00 导出含 4 个机房负荷层的复核报告，并排程于 19:30 分发给夜班维保。

## 算法与复核

按机房与计划负荷分层，每项伴随告警独立比较有无该告警两组的目标发生率（次/千监测小时）。先筛选两组监测时间和两组事件合计均达标的层，再用各层合计监测小时作共同权重标准化两组发生率。达标层粗率比使用同一批层的原始合计。至少两层达标且标准化对照发生率有正值才报告标准化率比。

每次分析在出结果前自动做逐台剔除复核：逐台去掉该机组的全部日期，沿用全量分析各告警原有的达标层与权重复算标准化率比，标出联查首位易主的机组。原层缺组、未达门槛或对照率归零时，该轮记原因，不换层凑排名。每台机组的结论实时落库，计算中断后只续跑未完成机组；接手续跑后，旧执行迟到的结果不得写入。全部机组都有结论或缺数原因后，联查页面才一次性切换到完整结果。

日期、负荷、告警目录、运行分钟或事件数不合规则需修订 CSV，重复机组日须回源去重。支持不足的层保留明细并标原因，对照率为零时率比留空。没有可报告的标准化率比时，计算结果保留供补数，批准和分发暂停。 复核问题为「在同机房和计划负荷的共同支持下，哪项伴随告警值得优先调阅机组日志，哪些层还需补齐监测资料？」。每次分析绑定数据版本和参数，原始数据按规范化内容的 SHA-256 去重。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `asset_id` | 机组编号 | str |
| `service_date` | 运行日期 | str |
| `room` | 机房 | str |
| `load_band` | 计划负荷档 | str |
| `runtime_minutes` | 有效监测运行分钟 | int |
| `coalarms` | 运行开始时的伴随告警 | str |
| `target_events` | 出水温度高新发事件数 | int |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18296`
- API 文档 `http://127.0.0.1:19296/docs`
- 数据库端口 `17796`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、运行分析、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、PostgreSQL 16 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
